## What We Tried

**Parallel store wiring (Phase 1):** All three stores were updated simultaneously since they had no shared data dependencies. This worked because each store had a clear API contract and the Stitch components were already consuming the store interfaces -- only the implementation layer changed.

**Manual chunk config vs dynamic imports (Phase 2):** Considered pushing more route-level React.lazy imports as the previous session did, but the bottleneck was not page-specific code -- it was library weight (antd, dayjs) shared across routes. manualChunks was the correct tool.

**Playwright codegen + manual assertion (Phase 3):** Generated locators via codegen, then hand-rolled the assertion logic. This is the right balance -- codegen for the painful locator discovery, manual effort for the test value.

## Root Cause Analysis

The loyalty field mapping issue is a symptom of a deeper problem: the Stitch export produced components against a mock schema, not the production API schema. The components assumed `points_balance` existed as returned by the mock, but the real API returns `points`. This divergence was invisible during development because the mock layer served the Stitch-native shape. Only when we swapped real API calls did the mismatch surface.

This is the fundamental risk of component-first development against synthetic data. The components look right, feel right, and pass visual QA -- but they are wired to a data contract that does not exist in production.

The chunk size persists because the Stitch component library bundles antd tables and date utilities that cannot be tree-shaken as separate chunks at the Vite level. A proper solution would be module-level chunk hints in the Stitch library itself, which we do not control.

## Lessons Learned

1. **Wire backend before visual polish, not after.** If we had wired real API calls during the initial Stitch integration, the 7 field mapping bugs would have been caught in that session instead of this one. Mock-first dev is fine for prototyping, but production wiring should happen before asset polishing because the polish effort is wasted if the data contract changes.

2. **The chunk warning is a noise tax, not a defect.** 879KB for a single-page app with antd, react-router, dayjs, and a custom component library is normal. The warning threshold of 500KB is Vite's conservative default for mobile-first thinking. We should either bump the threshold or suppress the warning and track it in CI as a trend. The warning noise in every build encourages ignoring warnings.

3. **E2E tests rot fast; focus assertions on data, not selectors.** Playwright codegen produces brittle locators (nested nth-child, chained role selectors). Every review should strip those back to data-testid or aria-label based selectors. 148 tests with fragile locators is worse than 50 tests with robust ones.

4. **Pipeline fatigue is real.** By the 4th pipeline in a session, decision quality drops. The loyalty field mapping fix took 3 attempts because the first two patches were myopic -- fixing the symptom in one component instead of the root mismatch in the store adapter. Reviewing the store contract first would have saved time. In hindsight, the fix rate slowed noticeably after pipeline 3.
